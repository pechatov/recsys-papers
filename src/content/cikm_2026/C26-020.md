## Коротко

Работа описывает production GNN для ранжирования рекомендаций друзей AI VK. Наиболее важны два сравнительно простых выбора: multi-hash таблица вместо отдельного embedding каждого user ID и дешёвый temporal neighbor sampling. Модель рассчитывает representations офлайн; онлайн ranker использует готовый GNN score. Это не full-graph message passing на каждом запросе и не content-feed ranker.

## Задача и мотивация

Социальные связи содержат больше полезной информации, чем небольшой профиль пользователя, но таблица на сотни миллионов ID требует более 200 GB. Message passing дополнительно разрастается на hubs. Если обучать impression-time prediction по последнему snapshot без временного ограничения, в соседство попадут ещё не существовавшие связи.

Цель — принять или не принять показанную рекомендацию друга, а не предсказать любую будущую связь среди всех пар пользователей. Positive label соответствует friend addition после impression; negatives включают отсутствие действия и hide. Upstream candidate generation фиксируется. Такая постановка приближена к production distribution, но её нельзя напрямую сравнивать с академическим link prediction по случайным отсутствующим рёбрам.

## Как работает метод

1. Начальное представление объединяет bucketized age/degree и gender с multi-hash ID. Три независимых hashes выбирают строки общей таблицы; embeddings конкатенируют, проецируют и нормируют. Вектор суммируют с feature representation.
2. Два слоя GATv2 с восемью attention heads агрегируют sampled neighborhood; hidden size 512. Отдельные query/candidate heads размерности 128 учитывают асимметрию ролей. Inner product используется для binary cross-entropy обучения.
3. На каждом hop выбирают до тридцати соседей. Для impression времени τ разрешены только edges раньше τ−Δ, где Δ=30 минут компенсирует задержку обновлений. Один cutoff τ сохраняют на всех hops, а не сдвигают по timestamp промежуточного ребра.
4. Adjacency lists CSR один раз сортируют по timestamp. Binary search находит допустимый prefix, из которого равномерно сэмплируют соседей: стоимость O(log degree+K) вместо scan O(degree+K). Это не устраняет offline стоимость первоначальной сортировки.
5. CPU Java/C++ sampler и GPU trainer разделены bounded queue/prefetch. CSR хранится в RAM, trainable state — на GPU. Periodic refresh записывает embeddings в serving storage; gradient-boosted ranker получает GNN score без request-time обхода многослойного графа.

## Эксперименты и результаты

Граф содержит 194 млн пользователей и 28 млрд записей рёбер; impression log — 1,4 млрд train и 25 млн test примеров с временным разделением. Train использует последние три года. Система работает на одном host: восемь A100 80GB, 512GB RAM и 64 CPU cores. Shared hash table имеет 2^21 строку по 256 координат; training batch — 1024 пары на GPU, Adam learning rate 0,0015.

Per-user ROC-AUC: Top-pop 0,5050, MF 0,5316, прежний WalkGNN 0,5572, новый GNN 0,6278. Full ID-table baseline занимает 202,88GB и даёт 0,6246; multi-hash — 2GB и 0,6278. Это подтверждает экономию памяти без потери качества в данном сравнении, но не доказывает превосходства hashing на любом графе.

Naive temporal sampling и binary-search вариант дают одинаковую AUC 0,6278, но sampling time/batch — 1473 и 595 мс. Non-temporal вариант имеет 0,5907 и 581 мс: утечка здесь сопровождается ухудшением, а не привычным завышением метрики. Поэтому временную корректность нельзя оценивать только направлением AUC-изменения.

CSR занимает 225GB, обучение до convergence — 63 часа, refresh embeddings всех пользователей — 6,57 часа. Двухнедельный production A/B даёт friend additions +16%, unique adders +11,5% с p<0,01. Feed time +0,28% — downstream эффект лучшей связности, не прямой результат смены feed ranker. P50/P90/P99 ranking latency не ухудшается.

## Ограничения и практический смысл

Авторы прямо признают cold window для новых и неактивных пользователей между переобучениями: hash collisions не заменяют отсутствующую supervision. Periodic offline refresh создаёт staleness; компромисс приемлем для сравнительно медленного friendship signal, но хуже подходит быстрым session interests.

Все результаты получены на закрытом production graph. Multi-hash — компрессия input ID-table, а не всего графа или всех cached output embeddings: RAM и refresh всё равно существенны. Для переноса полезно отдельно измерить hubs, новичков, давность refresh и качество upstream candidates. Работа ценна открытым VK-GNN framework и ясным разделением memory, temporal correctness и serving costs.

## Вопросы авторам

1. Как temporal correctness обеспечивается для node degree и других признаков snapshot, помимо отсечения будущих рёбер в sampler?
2. Как выбираются период retraining и refresh, и как меняется качество по времени после обновления и для пользователей cold window?
3. Что объясняет худшую AUC non-temporal модели: train–test mismatch, прямое target-edge contamination или изменение sampled neighborhood distribution?
4. Каков баланс памяти и качества при другом числе hash slots и более свежем частичном refresh, особенно для hubs и новых пользователей?
