> Разбор по полному arXiv:2609.07273v1 от 7 сентября 2026. Название, авторы Yuchen Wang, Feng Niu и соавторы и DOI в PDF соответствуют конференционной записи.

## Коротко

MORE, Multi-task cO-evolving Ranking modEl, устраняет task-blind общий backbone: сведения о задаче влияют на чтение последовательности, смешивание признаков и развитие представления на всех слоях. Shared Anchors собирают общее знание, Private Anchors — отличия задач. User sequence state остаётся независимым от кандидатов, что позволяет делить его вычисление между всеми товарами запроса.

## Задача и мотивация

Объединение sequence modeling и feature interaction ещё не делает ranker task-aware. Если click, comment и deep chat различаются только финальной головой, backbone вынужден выдавать одну компромиссную representation. Частые labels могут доминировать над редкими глубокими действиями. MORE переносит специализацию внутрь вычисления, сохраняя общие признаки и explicit task boundaries.

Работа исследует социальную ленту Momo Nearby Feed, где рекомендации должны одновременно поддерживать потребление контента и начало общения. Поэтому качество не сводится к CTR. Авторы сравнивают multi-task модели при общей framework, training schedule и hyperparameter budget, а масштабирование оценивают по параметрам и forward FLOPs.

## Как работает метод

1. Историю кодируют суммой item embedding, action-combination embedding и temporal embedding. Cartesian encoding превращает multi-hot сочетание поведений в отдельный action ID; так различия labels доступны уже input layer.
2. Shared и Private Anchors инициализируют из pooled history и non-sequential features. К каждому Private Anchor добавляют learnable task prior. Эти состояния проходят через все MORE blocks.
3. Task-Aware Sequence Reading обновляет общий sequence state через SwiGLU и использует его как K/V memory. Shared/private queries читают его по-разному; sequence register переносит компактную накопленную информацию между слоями через независимые gates.
4. Selective Semantic Mixing объединяет anchors с feature tokens MLP-Mixer-style операцией. Task-boundary mask не позволяет Private Anchors непосредственно смешиваться друг с другом; shared и feature channels сохраняют общий контекст. Per-token FFN и residual updates дополняют mixing.
5. Task Enhancing применяет отдельную FiLM-style affine modulation каждого private state по non-sequential features. Task towers получают частное и общее знание; weighted BCE суммируется по задачам. При request batching история вычисляется один раз, per-candidate anchors остаются отдельными.

## Эксперименты и результаты

Закрытые логи Momo за девяносто последовательных дней служат train, следующий день — evaluation. Основная метрика GAUC считается по пользователям. В setup заявлены тринадцать задач, в default configuration описаны девять Private и восемь Shared Anchors, а главная таблица публикует семь задач. Препринт не поясняет полностью соответствие этих трёх чисел; их нельзя автоматически считать одним и тем же набором целей.

Default model содержит два blocks, hidden dimension 256 и пятнадцать non-sequential tokens; optimizer Adam, batch 1024. Сравниваются Transformer+RankMixer/Wukong/DCNv2, HSTU+RankMixer, STCA, MixFormer, HyFormer и OneTrans. MORE использует 132M dense parameters и 1,85G FLOPs/example против 77,85M и 1,92G у reference Transformer+RankMixer.

Relative GAUC lifts над reference: click +0,44%, like +1,47%, comment +1,26%, greet +1,58%, reply +0,62%, avatar-click +1,02%, deep chat +0,33%. Удаление boundary mask даёт наибольшую среднюю деградацию одиночного компонента: −0,21%, в interaction-срезе −0,34%. Полное удаление новых механизмов снижает average GAUC на 0,33%. Scaling проверяется примерно от 0,1B до 0,9B dense parameters.

Двухнедельный A/B против production DLRM сообщает duration +3,0%, click +2,8%, like +2,0%, comment +3,6%, greet +2,5%, deep chat +2,0%; заявлена значимость p<0,05. Deep chat определяется как минимум пять раундов. Request-level sharing снижает P99 scoring latency примерно на 30% относительно per-candidate serving той же модели, а не обязательно против прежнего production ranker.

## Ограничения и практический смысл

Модель подтверждена на одном закрытом социальном сценарии; перенос на commerce и другую task structure оставлен будущей работе. Boundary mask ограничивает явный обмен private states, но не доказывает отсутствие gradient interference через общие параметры. Разная плотность labels и выбор BCE weights остаются существенными для итогового компромисса.

Для пилота стоит сравнить task-aware anchors с простым увеличением ёмкости heads и с task-conditioned sequence queries отдельно. Важно измерять не только среднюю GAUC, но и редкие глубокие действия, нагрузку каждой ветви и рост стоимости при добавлении задач. Инженерная ценность — явное разделение общего sequence computation и candidate-specific state, позволяющее увеличивать специализацию без повторного encoding всей истории.

## Вопросы авторам

1. Как соотносятся тринадцать оптимизируемых задач, девять Private Anchors и семь задач основной таблицы; какие цели используют общий или отдельный private state?
2. Какие измерения gradient conflict подтверждают пользу boundary mask сверх абляции итоговой GAUC, особенно между частыми и редкими labels?
3. Как растут память и latency при десятках задач и можно ли добавлять новый task anchor без переобучения всего backbone?
4. Каков эффект request sharing по распределению числа кандидатов и какая часть 30% P99 выигрыша сохраняется при маленьких mini-batches?
