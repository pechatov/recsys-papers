## Коротко

CAR обучает авторегрессионный retrieval учитывать несколько будущих горизонтов и управлять выдачей через целевой action token. Одна модель должна поддерживать разные бизнес-цели без отдельного retraining для каждой из них.

Обзор подготовлен по авторской аннотации в программе конференции; полный текст не проверен. Указанные ниже ограничения переноса — вопросы для проверки, а не приписываемые авторам результаты.

## Задача и мотивация

Обычный next-interaction objective близорук: он не отличает немедленное действие от долгосрочно полезного. Кроме того, цель candidate generation трудно менять на serving, если она зашита только в training labels. Авторы раздельно добавляют long-horizon supervision и явный интерфейс действия.

## Как работает метод

1. Long-term supervision module использует несколько action-sliding prediction heads на разных будущих горизонтах. Эти дополнительные задачи должны ввести информацию о последующем поведении, которого нет в единственной next-item метке.
2. P-CAR переносит знания через parameter sharing, а C-CAR использует cascading. Аннотация выделяет две формы связи вспомогательных предсказаний и основного генератора, но не раскрывает их точную архитектурную стоимость.
3. Action-induced input module перестраивает представление истории в action–item sequence. Модель видит тип действия отдельно от объекта, чтобы не смешивать разные намерения только через общий item identifier.
4. На inference подаётся target action token. Это условие направляет формирование recall set под выбранную цель без обязательного изменения весов модели для каждого запроса или продукта.

## Эксперименты и результаты

По аннотации, CAR оценивается на трёх публичных benchmark и двух промышленных наборах. Заявлены статистически значимые преимущества над сильными autoregressive baseline и online-A/B на QQ Music и WeSing; система развёрнута для сотен миллионов ежедневных пользователей. Конкретные uplift, набор actions, горизонты, длительность тестов и serving overhead в проверенном источнике не приведены, поэтому их нельзя достроить из названия метода.

## Ограничения и практический смысл

Для переноса нужно уточнить, какие действия доступны в логах и как обрабатывается delayed feedback. Управляемость по action token может работать только для целей, наблюдавшихся при обучении. Также важно проверить, действительно ли вспомогательные heads не создают утечку будущих событий в пользовательский inference-контекст.

Работа полезна retrieval-командам, обслуживающим несколько сценариев музыки или социальных действий. Пилот стоит строить с отдельными метриками немедленного и отложенного результата, а также с контролем candidate diversity. Это покажет, меняется ли качество долгосрочного поведения или модель просто перераспределяет кандидатов между уже хорошо представленными типами действий.

## Вопросы авторам

1. Как выбираются будущие горизонты action-sliding heads и учитывается цензурирование ещё не завершившихся пользовательских историй?
2. Какая разница между P-CAR и C-CAR по latency, training stability и переносу долгосрочного сигнала?
3. Можно ли задать новый target action без дообучения или управляемость ограничена известным vocabulary действий?
4. Как измеряется trade-off между целевым действием и общим engagement при смене action token на serving?
