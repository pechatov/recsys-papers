## Коротко

MUSER поддерживает долгосрочные и текущие интересы отдельным User Agent, а Recommendation Agent выбирает товар и формирует объяснение по компактному состоянию. Слово parametric здесь включает управляемый числовой параметр изменчивости интересов; пользовательская память также явно хранится во внешней базе и содержит текстовые пункты профиля.

## Задача и мотивация

Большая мультимодальная модель не может каждый раз перечитывать растущую историю. Простое рекурсивное суммирование способно вытеснять старые интересы и сглаживать их различия. Авторы предлагают персонализировать скорость изменения памяти и учить рекомендателя одновременно воспроизводить решение и reasoning teacher-модели. Это система управления состоянием пользователя, а не новый формат semantic ID.

## Как работает метод

1. User Agent выделяет short-term интересы из очередного мультимодального batch и сопоставляет их с long-term памятью. LLM выдаёт пятибалльную оценку семантического отклонения; детерминированное преобразование переводит её в диапазон −0,5…0,5.
2. Параметр Pper обновляется асимметричным экспоненциальным правилом с ограничением [0,1]. Он управляет инструкциями добавления, забывания и перестановки элементов памяти. Численные операции и сохранение состояния выполняют внешние Python-инструменты, а не арифметика LLM.
3. Recommendation Agent получает сохранённые LTI/STI, Pper и мультимодальные признаки кандидатов. Он авторегрессионно выдаёт решение и текст объяснения.
4. LoRA-обучение студента использует отдельные decision и rationale losses по последовательностям teacher. Dual Consistency Regularization меняет их веса по отношению confidence; это proxy согласованности, а не независимая проверка истинности объяснения.

## Эксперименты и результаты

Эксперименты используют MicroLens, MovieLens-Small с постерами и Bili_Movie, временное разделение, AUC и Recall/MRR/NDCG@10. Детали candidate sampling в статье недостаточны для точного восстановления evaluation pool. Студенты LLaVA-NeXT 7B/13B/34B проверяются с teacher 7B и 685B; основная таблица использует сильную teacher-супервизию.

В таблице 2 MicroLens AUC равен 0,8856. Наиболее сильный baseline по этому показателю — MUSE с 0,8239, тогда как MLLM-MSR имеет 0,7751. Указанные +7,49% соответствуют первому сравнению; их нельзя приписывать сравнению только с MLLM-MSR. На MovieLens NDCG@10 составляет 0,4795 против 0,4296 у MLLM-MSR, на Bili_Movie — 0,6476 против 0,5850.

Абляция таблицы 4 на MicroLens поднимает AUC с 0,7751 до 0,8364 после добавления User Agent, затем до 0,8856 у полной системы. Таблица 3 оценивает объяснения GPT-4/GPTScore, BLEU и ROUGE. На MovieLens ROUGE-1/2 полной модели немного ниже LLaVA: 0,3688/0,1010 против 0,3692/0,1017. Универсального выигрыша по всем explanation-метрикам нет.

Раздел 4.6 сообщает latency на MovieLens 72,5 мс против 185,5 мс у MLLM-MSR, но лёгкие sequential/search модели работают примерно за 10 мс. Дорогая консолидация User Agent выполняется offline или между сессиями, поэтому 72,5 мс не описывает весь жизненный цикл обновления памяти.

## Ограничения и практический смысл

Полезная инженерная идея — разделить редкое обновление состояния и частую оценку кандидатов. Приложение показывает конкретные шаблоны профиля и памяти. Однако компактная текстовая память всё ещё сжимает историю; заявление о неограниченном горизонте не гарантирует сохранности каждого старого предпочтения.

Моя критическая оценка: оценка объяснений другой LLM и лексическим пересечением не доказывает их причинную верность. Короткие средние истории MicroLens и Bili_Movie также ограничивают доказательства lifelong-моделирования. Для production нужно учитывать размер candidate list, стоимость User Agent, персональное хранение, устаревание профиля и online A/B, которого эти benchmark-результаты не заменяют.

## Вопросы авторам

1. Как измерить причинную верность объяснений независимо от GPTScore и teacher-подобия, например при контролируемом удалении отдельных интересов из памяти?
2. Какова end-to-end стоимость с учётом консолидации User Agent и хранилища при миллионах активных пользователей?
3. Как меняются latency и качество при увеличении candidate set, и какие кандидаты использованы в основных ranking-метриках?
4. Может ли Pper восстанавливаться после долгого периода случайных или ошибочных действий, не теряя устойчивые редкие интересы?
